SECTION 01

What Is Function Calling?

By default, Claude can only read and write text. It can't check your calendar, send an email, query a database, or look up live data. Function calling (also called tool use) is the bridge that lets Claude trigger real actions in the real world.

💡

Simple analogy: Imagine Claude is a very smart colleague who works remotely. You give them a list of "tools" they can request — like "send email", "book meeting", "check stock price". When they need one, they write you a note saying "please run send_email with these details". You run it and tell them the result. That back-and-forth is function calling.

Why does it exist?

LLMs have a knowledge cutoff and no access to the outside world. Function calling lets you extend Claude with any capability you build — sending emails, querying APIs, reading files, controlling software. The model decides when to use a tool; you decide what tools exist and how they actually run.

✅

Key insight: Claude does NOT actually execute the function. It only tells you what function to call and with what arguments. Your code runs the function, then reports the result back to Claude.

SECTION 02

The Mental Model — The Full Loop

Function calling is a multi-turn conversation. Think of it as a loop with 5 steps:

1
You define tools + send the user message
You tell Claude what tools exist (their names, descriptions, parameters) and ask a question like "Send an email to Alice about tomorrow's meeting."
YOUR CODE → API
2
Claude decides to use a tool
Claude sees the tools, determines that send_email is appropriate, and responds with stop_reason: "tool_use" — it lists the function name and the arguments it wants to pass.
API → YOUR CODE
3
You execute the function
Your code reads the arguments Claude provided, actually calls send_email (or whatever the tool does), and captures the result (success, error, data returned).
YOUR CODE (local execution)
4
You return the result to Claude
You send a new API request with the full conversation history PLUS the tool result, so Claude knows what happened.
YOUR CODE → API
5
Claude gives a final answer
Claude now responds with stop_reason: "end_turn" and gives a human-readable reply like "Done! I've sent the email to Alice."
API → YOUR CODE → User
⚠️

Remember: This is always at least 2 API calls — one to get the tool call from Claude, one to give Claude the result. The loop can continue if Claude needs to call multiple tools.

SECTION 03

Defining a Tool — The Schema

You describe tools to Claude using JSON Schema. Claude reads these descriptions to understand what tools are available and when to use them.

The tool object structure

name
required
The function's identifier. Use snake_case. e.g. send_email
description
recommended
Explains what the tool does. Claude uses this to decide WHEN to call it. Write it clearly.
input_schema
required
A JSON Schema object describing the function's parameters — their types, descriptions, and which are required.

A complete send_email tool definition

Tool Definition JavaScript
const tools = [
  {
    name: "send_email",           // ← required, snake_case

    description: "Sends an email to one or more recipients.
    Use this when the user wants to compose and send an email.",

    input_schema: {
      type: "object",              // always "object" at top level

      properties: {
        to: {
          type: "string",
          description: "Recipient email address"
        },
        subject: {
          type: "string",
          description: "Email subject line"
        },
        body: {
          type: "string",
          description: "Email body content"
        },
        cc: {                          // ← optional field
          type: "array",
          items: { type: "string" },  // array of strings
          description: "CC recipients"
        }
      },

      required: ["to", "subject", "body"]  // ← cc is NOT here = optional
    }
  }
];
💡

How optional fields work: In JSON Schema, a field is optional simply by leaving it OUT of the required array. There is no optional: true or required: false property — those don't exist in the spec.

Common JSON Schema types

TypeExampleUse for
string"hello"Text, emails, names, IDs
number42, 3.14Amounts, counts, coordinates
booleantrue / falseFlags, toggles
array["a", "b"]Lists. Needs an items property to describe element type
object{ "key": "val" }Nested structures. Needs its own properties
SECTION 04

Making the API Request

You pass your tools array in the request alongside the messages. The API handles the rest.

API Request (Call 1) JavaScript
const response = await fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "x-api-key": "YOUR_API_KEY",
    "anthropic-version": "2023-06-01"
  },
  body: JSON.stringify({
    model: "claude-sonnet-4-20250514",
    max_tokens: 1024,
    tools: tools,           // ← your tool definitions array
    messages: [
      {
        role: "user",
        content: "Send an email to alice@example.com about tomorrow's 10am meeting"
      }
    ]
  })
});

const data = await response.json();
SECTION 05

Parsing the Response

When Claude wants to call a tool, the response looks like this:

API Response — Tool Use JSON
{
  "id": "msg_01abc",
  "type": "message",
  "role": "assistant",
  "stop_reason": "tool_use",   // ← THIS tells you a tool was requested

  "content": [
    {
      "type": "tool_use",         // ← block type
      "id": "toolu_01xyz",       // ← SAVE THIS — you'll need it in step 4!
      "name": "send_email",      // ← which function to call
      "input": {                  // ← the arguments
        "to": "alice@example.com",
        "subject": "Meeting tomorrow at 10am",
        "body": "Hi Alice, just a reminder about our meeting tomorrow at 10am."
      }
    }
  ]
}

How to extract the tool call in your code

Parsing the tool call JavaScript
// 1. Check if Claude wants to use a tool
if (data.stop_reason === "tool_use") {

  // 2. Find the tool_use block in content
  const toolUseBlock = data.content.find(
    block => block.type === "tool_use"
  );

  // 3. Extract what you need
  const toolName = toolUseBlock.name;    // "send_email"
  const toolId   = toolUseBlock.id;      // "toolu_01xyz" — keep this!
  const args     = toolUseBlock.input;  // { to, subject, body }

  // 4. Access specific arguments
  const recipient = args.to;       // "alice@example.com"
  const subject   = args.subject;  // "Meeting tomorrow at 10am"
}
🚨

Critical distinction: The arguments are in .input, NOT .parameters or .arguments. This is the Anthropic API — other APIs (like OpenAI) use different field names. Getting this wrong is a very common mistake.

Stop reason values — what they mean

stop_reasonMeaningWhat to do
"end_turn"Claude finished normallyShow the response to the user
"tool_use"Claude wants to call a functionExecute the function, return result
"max_tokens"Hit the token limit mid-responseIncrease max_tokens or handle gracefully
SECTION 06

Returning the Tool Result

After you run the function, you send Claude the result by making a second API request. This time, the messages array includes the entire conversation history — the original user message, Claude's assistant response, and your tool result.

💡

Anthropic vs OpenAI — important difference: In the Anthropic API, tool results are sent as a user role message with a tool_result content block. OpenAI uses a tool role. This is a key exam question.

API Request (Call 2) — sending the result back JavaScript
// First, actually run your email function
const emailResult = await sendEmail(args.to, args.subject, args.body);

// Then send the full conversation + result back to Claude
const response2 = await fetch("https://api.anthropic.com/v1/messages", {
  method: "POST",
  // ... headers ...
  body: JSON.stringify({
    model: "claude-sonnet-4-20250514",
    max_tokens: 1024,
    tools: tools,
    messages: [

      // 1. Original user message
      {
        role: "user",
        content: "Send an email to alice@example.com about tomorrow's meeting"
      },

      // 2. Claude's response (the tool_use block) — include it as-is
      {
        role: "assistant",
        content: data.content   // the whole content array from response 1
      },

      // 3. Your tool result — ALWAYS role: "user"
      {
        role: "user",            // ← NOT "tool", NOT "function" — always "user"
        content: [
          {
            type: "tool_result",
            tool_use_id: toolId,  // ← must match the id from the tool_use block!
            content: "Email sent successfully to alice@example.com"
          }
        ]
      }
    ]
  })
});
✅

The tool_use_id is critical. It links the result to the specific tool call Claude made. If you use the wrong ID (or omit it), Claude can't understand which function was run and the conversation breaks. Always save the id from the tool_use block.

SECTION 07

Error Handling

What if sending the email fails? You should tell Claude about the failure so it can respond appropriately. Do this with is_error: true in the tool_result block.

✓ CORRECT — sending an error result
{
  role: "user",
  content: [{
    type: "tool_result",
    tool_use_id: toolId,
    is_error: true,
    content: "SMTP error: 
    connection refused"
  }]
}
✗ WRONG — skipping the tool result
// DO NOT just send a new 
// user message like this:
{
  role: "user",
  content: "The email 
  failed to send"
}
// Claude won't know this
// is a tool result

When is_error: true, Claude knows the function failed and can tell the user, suggest alternatives, or retry differently.

Full error handling pattern

Robust error handling JavaScript
let toolResultContent;

try {
  const result = await sendEmail(args.to, args.subject, args.body);
  toolResultContent = {
    type: "tool_result",
    tool_use_id: toolId,
    content: `Email sent successfully. Message ID: ${result.messageId}`
  };
} catch (error) {
  toolResultContent = {
    type: "tool_result",
    tool_use_id: toolId,
    is_error: true,                   // ← flag the failure
    content: `Failed to send email: ${error.message}`  // ← error details
  };
}
SECTION 08

Complete End-to-End Walkthrough

Here is the entire send_email flow, start to finish, in one file.

complete-email-tool.js Full example
// ─────────────────────────────────────────────
// STEP 1: Define your tool
// ─────────────────────────────────────────────
const tools = [{
  name: "send_email",
  description: "Sends an email to a recipient",
  input_schema: {
    type: "object",
    properties: {
      to:      { type: "string", description: "Recipient email" },
      subject: { type: "string", description: "Email subject"   },
      body:    { type: "string", description: "Email body"      }
    },
    required: ["to", "subject", "body"]
  }
}];

// ─────────────────────────────────────────────
// STEP 2: First API call — ask Claude to help
// ─────────────────────────────────────────────
const userMessage = "Send an email to alice@example.com about tomorrow's 10am meeting";

const res1 = await callAPI([{ role: "user", content: userMessage }]);

// ─────────────────────────────────────────────
// STEP 3: Check if Claude wants to use a tool
// ─────────────────────────────────────────────
if (res1.stop_reason === "tool_use") {

  const toolCall = res1.content.find(b => b.type === "tool_use");
  const { id, name, input } = toolCall;

  // id    = "toolu_01xyz"
  // name  = "send_email"
  // input = { to, subject, body }

  // ─────────────────────────────────────────────
  // STEP 4: Run the actual function
  // ─────────────────────────────────────────────
  let resultText;
  let isError = false;

  try {
    await sendEmailViaAPI(input.to, input.subject, input.body);
    resultText = "Email sent successfully";
  } catch (e) {
    resultText = e.message;
    isError = true;
  }

  // ─────────────────────────────────────────────
  // STEP 5: Send result back — second API call
  // ─────────────────────────────────────────────
  const res2 = await callAPI([
    { role: "user", content: userMessage },
    { role: "assistant", content: res1.content },
    {
      role: "user",             // ← ALWAYS "user" for tool results
      content: [{
        type: "tool_result",
        tool_use_id: id,       // ← match the id from step 3
        content: resultText,
        ...(isError && { is_error: true })
      }]
    }
  ]);

  // ─────────────────────────────────────────────
  // STEP 6: Claude gives final answer
  // ─────────────────────────────────────────────
  // res2.stop_reason === "end_turn"
  // res2.content[0].text === "Done! I've sent the email to Alice."
  console.log(res2.content[0].text);
}
SECTION 09

Common Mistakes to Avoid

Mistake Wrong Correct
Wrong field for arguments .parameters or .arguments .input
Wrong role for tool result role: "tool" or "function" role: "user"
Optional field schema required: false inside property Omit from the required[] array
Missing tool_use_id Omitting the ID in tool_result Always include tool_use_id matching the call
Wrong stop_reason check "function_call" "tool_use"
Skipping error signal Sending a plain user message on failure Use is_error: true in tool_result
Array of strings schema type: "string[]" type: "array", items: { type: "string" }
⚠️

Remember the context: Turing tests specifically cover the Anthropic API. If you've seen OpenAI function calling before, be careful — several field names and patterns are different. When in doubt, think: Anthropic uses "user" role and ".input", not "tool" role and ".arguments".

SECTION 10

Multiple Tools — Claude Choosing Between Them

In real applications, you'll define several tools at once. Claude reads the description of each tool and decides which one (if any) to call based on the user's request. The description is how Claude makes the decision — write it precisely.

Defining multiple tools JavaScript
const tools = [
  {
    name: "send_email",
    description: "Send an email to a recipient. Use when the user wants to SEND a message.",
    input_schema: {
      type: "object",
      properties: {
        to:      { type: "string", description: "Recipient email address" },
        subject: { type: "string", description: "Email subject line" },
        body:    { type: "string", description: "Email body content" }
      },
      required: ["to", "subject", "body"]
    }
  },
  {
    name: "search_inbox",
    description: "Search emails in the inbox. Use when the user wants to FIND or READ emails.",
    input_schema: {
      type: "object",
      properties: {
        query:  { type: "string", description: "Search keywords" },
        limit:  { type: "number", description: "Max results (default 10)" }
      },
      required: ["query"]  // limit is optional
    }
  },
  {
    name: "create_draft",
    description: "Save an email as a draft without sending. Use when the user wants to SAVE for later.",
    input_schema: {
      type: "object",
      properties: {
        to:      { type: "string" },
        subject: { type: "string" },
        body:    { type: "string" }
      },
      required: ["to", "subject", "body"]
    }
  }
];
💡

Tool selection is driven by description. If a user says "find the email from Bob last week", Claude picks search_inbox. If they say "send this to Bob", Claude picks send_email. The description is your contract with Claude about when to use each tool.

What if no tool is needed?

If Claude decides the user's request doesn't require any tool (e.g., "What time is it in New York?"), it just responds with stop_reason: "end_turn" and a plain text answer. Your code should handle both cases.

Handling both outcomes JavaScript
if (response.stop_reason === "tool_use") {
  // Claude wants to call a tool — handle it
  const toolCall = response.content.find(b => b.type === "tool_use");
  // dispatch based on which tool was chosen
  if (toolCall.name === "send_email")    await handleSendEmail(toolCall);
  if (toolCall.name === "search_inbox")  await handleSearch(toolCall);
  if (toolCall.name === "create_draft")   await handleDraft(toolCall);

} else if (response.stop_reason === "end_turn") {
  // No tool needed — show the text response directly
  const text = response.content.find(b => b.type === "text").text;
  console.log(text);
}
SECTION 11

tool_choice — Controlling Which Tool Claude Uses

By default, Claude decides whether to use a tool. But you can override this behaviour with the tool_choice parameter.

tool_choice value Behaviour When to use
{ type: "auto" } Default. Claude decides whether to use a tool. Most conversations
{ type: "any" } Claude MUST call at least one tool, but picks which one. When you always need a structured output
{ type: "tool", name: "send_email" } Claude MUST call exactly this specific tool. When you know exactly which tool is needed
Using tool_choice in the request JavaScript
// Force Claude to always use send_email
body: JSON.stringify({
  model: "claude-sonnet-4-20250514",
  max_tokens: 1024,
  tools: tools,
  tool_choice: { type: "tool", name: "send_email" },  // ← forced
  messages: [...]
})

// Force Claude to use some tool (but Claude picks which)
tool_choice: { type: "any" }

// Let Claude decide (default — you can omit this)
tool_choice: { type: "auto" }
⚠️

Exam trap: tool_choice takes an object with a type field — not a plain string. Writing tool_choice: "auto" is wrong. Always write tool_choice: { type: "auto" }.

SECTION 12

Parallel Tool Calls — Claude Calls Multiple Tools at Once

Claude can request more than one tool in a single response. This happens when tasks are independent and can be done simultaneously. For example: "Search my inbox for Bob's email AND send a reply to Alice."

What a parallel response looks like

Response with multiple tool_use blocks JSON
{
  "stop_reason": "tool_use",
  "content": [
    {
      "type": "tool_use",
      "id": "toolu_01",             // ← first tool call
      "name": "search_inbox",
      "input": { "query": "Bob" }
    },
    {
      "type": "tool_use",
      "id": "toolu_02",             // ← second tool call
      "name": "send_email",
      "input": {
        "to": "alice@example.com",
        "subject": "Reply",
        "body": "Hi Alice!"
      }
    }
  ]
}

How to handle and return multiple results

You run BOTH functions (in parallel or sequentially), then return ALL results in a single "user" message — one tool_result block per call, each with its own tool_use_id.

Processing parallel calls + returning both results JavaScript
// 1. Collect all tool_use blocks
const toolCalls = response.content.filter(b => b.type === "tool_use");

// 2. Execute all tools (can run in parallel with Promise.all)
const results = await Promise.all(
  toolCalls.map(async (call) => {
    try {
      const output = await runTool(call.name, call.input);
      return {
        type: "tool_result",
        tool_use_id: call.id,      // ← match each call's id
        content: output
      };
    } catch (e) {
      return {
        type: "tool_result",
        tool_use_id: call.id,
        is_error: true,
        content: e.message
      };
    }
  })
);

// 3. Return ALL results in ONE user message
const nextRequest = {
  role: "user",
  content: results   // ← array of BOTH tool_result blocks
};
✅

Key rule: All tool results for a parallel batch go into one user message with multiple tool_result blocks. Don't send them as separate messages — that breaks the conversation structure.

Mixed responses — text + tool_use together

Claude can also return a text block alongside a tool_use block. For example, it might say "Sure, I'll send that email now!" and simultaneously request the tool call.

Mixed content response JSON
{
  "stop_reason": "tool_use",
  "content": [
    { "type": "text",     "text": "Sure! Sending that now..." },
    { "type": "tool_use", "id": "toolu_01", "name": "send_email", "input": {...} }
  ]
}

Always check stop_reason first — if it's "tool_use", there's a tool call to process, regardless of whether there's also a text block.

SECTION 13

Advanced JSON Schemas

Medium and Hard tests often include more complex parameter types. Here are the ones you need to know.

Enum — restricting to specific values

Enum type JSON Schema
priority: {
  type: "string",
  enum: ["low", "normal", "high", "urgent"],  // Claude can only choose one of these
  description: "Email priority level"
}

Array of objects — e.g., list of attachments

Array of objects JSON Schema
attachments: {
  type: "array",
  items: {
    type: "object",
    properties: {
      filename: { type: "string" },
      url:      { type: "string" }
    },
    required: ["filename", "url"]
  },
  description: "List of file attachments"
}

Nested object — e.g., sender details

Nested object JSON Schema
sender: {
  type: "object",
  properties: {
    name:  { type: "string", description: "Sender display name" },
    email: { type: "string", description: "Sender email address" }
  },
  required: ["email"]
}

strict: true — guaranteed schema validation

Strict mode tool definition JavaScript
{
  name: "send_email",
  description: "...",
  strict: true,                // ← Claude MUST follow the schema exactly
  input_schema: { ... }
}

With strict: true, Claude is guaranteed to produce tool inputs that match your schema exactly — no missing fields, no extra fields. Useful in production where invalid inputs would cause failures.

HARD LEVEL — Sections 14–16
SECTION 14

The Agentic Loop

Hard-level tasks involve agents — Claude that can take multiple actions in sequence until the job is done. The key pattern is a while loop: keep calling the API until stop_reason === "end_turn".

💡

Email agent example: "Find Bob's latest email and reply to it with a summary." This requires: (1) search_inbox, (2) read the result, (3) create a reply with send_email. Claude decides each step. The agentic loop keeps running until it's done.

Agentic loop pattern JavaScript
async function runAgent(userMessage) {
  const messages = [{ role: "user", content: userMessage }];

  // ─── THE LOOP ───────────────────────────────
  while (true) {
    const response = await callClaudeAPI(messages);

    // Add Claude's response to history
    messages.push({
      role: "assistant",
      content: response.content
    });

    // ✅ Done? Return the final answer
    if (response.stop_reason === "end_turn") {
      const text = response.content.find(b => b.type === "text")?.text;
      return text;
    }

    // 🔧 Tool call needed — handle it
    if (response.stop_reason === "tool_use") {
      const toolCalls = response.content.filter(b => b.type === "tool_use");

      const toolResults = await Promise.all(
        toolCalls.map(async call => {
          const result = await executeTool(call.name, call.input);
          return {
            type: "tool_result",
            tool_use_id: call.id,
            content: result
          };
        })
      );

      // Add results to messages — loop continues
      messages.push({
        role: "user",
        content: toolResults
      });
    }
  // ← loop runs again with updated messages
  }
}
✅

The pattern in plain English: 1) Ask Claude. 2) If it wants a tool, run it and add the result. 3) Ask Claude again (with full history). 4) Repeat until Claude says it's done (end_turn). The history grows with every loop iteration.

SECTION 15

System Prompts with Tools

You can give Claude a system prompt to set its persona, constraints, or instructions — even when using tools. This is common in real applications.

Request with system prompt + tools JavaScript
JSON.stringify({
  model: "claude-sonnet-4-20250514",
  max_tokens: 1024,
  system: "You are an email assistant for Acme Corp.
  Only send emails to addresses that end in @acme.com.
  Always use a professional tone.",    // ← system prompt
  tools: tools,
  messages: [
    { role: "user", content: "Send a meeting invite to the team" }
  ]
})
💡

The system prompt applies to all turns in the conversation — you don't need to repeat it. It's passed once at the top level of the request, not inside the messages array.

SECTION 16

Identifying the Correct Tool + Payload

The Turing assessment specifically tests: "given a user message and a set of tools, identify the correct tool AND the correct JSON payload." This is the most practical skill — you need to mentally simulate what Claude would do.

How to approach any scenario question

1
Read the user message carefully
What does the user actually want? Send, search, draft, or something else?
2
Match intent to tool description
Read each tool's description. Which one's purpose matches the user's intent? Don't rely on name alone — read the description.
3
Fill required parameters from the message
Pull values directly from what the user said. If a value isn't mentioned, check if the param is optional — if so, omit it; if required, Claude would ask.
4
Validate types match the schema
If the schema says type: "array" for cc, the payload should have "cc": ["x@y.com"], not a plain string.

Worked example

📋

User says: "Send an email to hr@company.com and finance@company.com asking about the Q3 budget. CC my manager at mgr@company.com."

Given these tools: send_email (with fields: to, subject, body, cc[]), create_draft, search_inbox — the correct answer is:

Correct tool call payload JSON
{
  "name": "send_email",      // ← user wants to SEND, not draft or search
  "input": {
    "to": "hr@company.com",    // ← first recipient (or array if schema allows)
    "subject": "Q3 Budget Inquiry",
    "body": "Hi, I wanted to ask about the Q3 budget...",
    "cc": ["mgr@company.com"]  // ← array, because schema type is "array"
  }
}

Common traps in scenario questions

TrapWrong thinkingCorrect thinking
Multiple recipients Put both in to as a string: "hr@..., fin@..." Check if to is type array or string — if string, one address; if array, list them
"Save for later" Use send_email Use create_draft — the user didn't say send
Missing optional field Set cc: null or cc: "" Simply omit the cc field entirely if there's no CC
Subject not mentioned Leave subject empty string "" Claude would infer/generate a reasonable subject from context
Two independent tasks One tool call for the first task only Parallel tool calls — Claude returns two tool_use blocks
